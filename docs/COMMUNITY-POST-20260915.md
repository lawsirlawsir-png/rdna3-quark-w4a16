# 在 Radeon PRO W7800（gfx1100）上跑 AMD 原版 Quark INT4 模型：一份可複核的實測報告

> 2026-09-15 ｜ 硬體：AMD Radeon PRO W7800 48GB（gfx1100 / RDNA3，70 CU）｜ ROCm 7.2.4 ｜ Ubuntu 24.04

---

## 〇、這篇要講什麼

AMD 在 HuggingFace 放出了 `amd/Qwen3.8-27B-Quark-AWQ-INT4-W4A16`，模型卡附完整評測數據。問題是：**它在 RDNA3 上跑不起來**。SGLang 的 Quark 模組只實作了 `w4a4_mxfp4`、`w4a8_mxfp4`、`w8a8_fp8` 三種 scheme，純 W4A16 沒有實作——`weights.py` 裡甚至直接註明「Scheme didn't allocate the parameter (e.g. W4A16)」。

我們寫了一個轉換器，把 Quark 的 **N-packed `[K, N/8]`** 佈局重新打包成 GPTQ 的 **K-packed `[K/8, N]`**，SGLang 便能以既有的 GPTQ 路徑服務它。**權重本身一個位元都沒有改。**

這篇報告有三部分：**怎麼做**（含一個容易踩的坑）、**量到什麼**（含我們自己發現的問題）、**以及我們誠實交代不確定的部分**。

---

## 一、轉換的關鍵：Quark 的 nibble 重排

這一步是整個工作的技術核心，也是我們當初卡最久的地方。

Quark 在 `pack_method="reorder"` 之下，每個 int32 內的 8 個 4-bit 值**不是順序排列**，而是按 `order_map = [0, 2, 4, 6, 1, 3, 5, 7]` 重排。忽略這一步，整個模型會輸出亂碼——不是數值偏差，是完全不可讀。

我們最初的版本就是漏了這一步，靠數值 sweep 猜 nibble 語義兜了好幾小時。**最後一讀官方 `quark/torch/utils/pack.py` 就中了。** 這件事讓我們確立了一條紀律：凡涉及外部格式，先讀官方實作，不要靠試探。

轉換器的完整邏輯（含 unpack 的 `ORDER=[0,4,1,5,2,6,3,7]`、signed int4 補數、以及與 GPTQ kernel 的 zero-point 對齊）已寫在我們的記錄裡，本文末尾附上要點。

### 無損驗證（三條獨立證據）

| 檢驗 | 結果 |
|---|---|
| 逐元素反量化比對（抽驗 5 層，含 K=5120／N=17408 與 N=48 的極瘦層） | **max 絕對差 = 0.000000e+00** |
| 全層覆蓋 | **496 個量化層 ＋ 703 個普通層**，全數通過 |
| 對 BF16 原模型的忠實度（96 個 `in_proj` 模組） | cos **最小 0.9871、中位 0.9905** |

第三項特別有意義：它顯示 AWQ 量化本身是正常的——dequant 後與 BF16 原模型的餘弦相似度都在 0.987 以上。

**⇒ 我們服務的，就是 AMD 原版的權重，逐位元相同。**

## 三、分數（含我們自己發現的問題）

### 3.1 Wikitext 困惑度

| 配置 | word_perplexity |
|---|---|
| **我們（INT4，權重 = AMD 原版）** | **9.7297** |
| AMD Quark AWQ（官方卡） | 8.8250 |
| AMD BF16 base（官方卡） | 8.4364 |

我們另外驗證了兩件事，結果都是「不影響」：
- **把 LM head 從 INT4 換成 BF16：9.7297 → 9.7297**（完全相同）
- **關掉我們自己加的 K-split 優化：9.7297 → 9.7296**

### 3.2 GSM8K 5-shot（non-thinking）

| 跑分 | 題數 | flexible-extract | strict-match |
|---|---|---|---|
| 第一次 | 1319 | **84.08%** | **84.76%** |
| 第二次 | 1319 | **83.32%** | **83.47%** |
| **AMD 官方卡（sampling）** | 1319 | **91.51%** | **90.37%** |

### 3.3 一個必須講清楚的問題：我們的 greedy 解碼不確定

上表兩次跑分**都用 greedy（`do_sample=False`）**，理應完全一致，卻差了 0.76 個百分點。

我們於是做了對照：**同一部伺服器、同一配置、同樣 150 題，連跑兩次**。

| 指標 | 結果 |
|---|---|
| 輸出完全相同 | **107 / 150（71.3%）** |
| 對錯翻轉 | **3 題** |
| 兩次分數 | 85.33% vs 84.67% |

**⇒ 結論：在我們的技術棧上，greedy 解碼是非確定的。** 因此：

- **單次跑分 = 真分數 + 噪音。** 我們自身噪音約 ±1 個百分點。
- 上面 83.32% 與 84.08% 的差異**不是**任何配置改動造成的，是 run-to-run 差異。
- **所以我們不報單一數字。兩次全量的平均是 flexible 83.70%、strict 84.12%。**

我們懷疑來源是 split-K 的 **CAS 原子累加**（加法次序不固定，捨入因而不定），或 LM head 低位寬路徑的 `M <= 8` 閘令精度隨 batch 大小跳變。**兩者皆未驗證，僅列為後續。**

## 四、與 AMD 公布數字的差距，以及我們的不確定

我們與 AMD 官方卡的三項差距：

| 指標 | 我們 | AMD | 差 |
|---|---|---|---|
| Wikitext PPL | 9.7297 | 8.8250 | **+10.25%** |
| GSM8K flexible | 83.70%（兩次平均） | 91.51% | **−7.81 pt** |
| GSM8K strict | 84.12%（兩次平均） | 90.37% | **−6.25 pt** |

**而我們已經排除的：**

| 嫌疑 | 排除方式 |
|---|---|
| 權重量化 | 逐位元相同（max 絕對差 = 0） |
| LM head | PPL 換 BF16 完全不變 |
| 量測儀器 | echo 路徑與原生 `/generate` 逐篇位元相同（0.000%） |
| 資料集 | wiki-2 與 wiki-103 的 test split **sha 相同**（62/62） |
| prompt 截斷 | 超長僅 0.61%，缺答案格式僅 0.30% |
| 我們自己的 K-split 優化 | 關掉後 9.7296（−0.00%） |

**⇒ 差距真實存在，但機制我們尚未定位。我們不猜。**

**兩點必須提醒讀者：**
1. **解碼制度不同**：我們用 greedy，AMD 用 `temperature=0.7, top_p=0.80, top_k=20, presence_penalty=1.5`。這個比較尚未對齊。
2. **我們有三條線索指向「服務路徑」而非權重**：① 同一份權重換一個量化配方（AutoRound）在同一 runtime 上得到更好的 PPL（9.4628 < 9.7297）② 我們 kernel 的拆解顯示 WMMA 路徑效率偏低 ③ 上游 vLLM 已改用完全不同的 kernel 結構（見下節）。

## 五、一個我們在拆解時發現的上游差異

我們把生產 `.so` 的 GPU 機器碼拆出來反匯編，發現 M≥16 的 WMMA kernel 中：

| 指令 | 條數 |
|---|---|
| `v_wmma`（真正的矩陣乘法） | **1** |
| `s_waitcnt`（等待） | **49** |
| └ `lgkmcnt(0)`（等齊全部） | **27** |
| `ds_load_u16_d16` 與 `_hi`（2 位元組 LDS 讀取） | **8 + 8 = 16** |

那 16 個 2 位元組讀取，正好對應原始碼裡的 `for (i=0..15) b_frag[i] = b_tile[i][lane_lo]`。

**編譯器並非無能**——它在別處懂得用 `lgkmcnt(1)`、`(2)`、`(7)` 等局部等待；是這段存取模式令它只能選擇最保守的做法。

**而上游 vLLM 已經不再用這條 kernel 服務 W4A16**：其 `rdna_hybrid_w4a16.py` 明寫 **M≤5 走專用 INT4 skinny GEMM（`wvSplitK_int4_g`，wave-level 分工 ＋ DPP 歸約、無原子競爭），M>5 走 Triton 融合 dequant GEMM**。

我們自己的生產情境有 **80% 的 decode GEMM 是 M=4**，正好落在 vLLM 那條分流的第一段。**這是我們下一步要量的。**

## 七、一句話總結

**我們把 AMD 原版 Quark INT4 模型無損地跑在 RDNA3 上了，速度可用（74 t/s）；但我們的服務品質低於 AMD 公布的數字，而我們已經排除了權重、LM head、量測儀器、資料集與自身優化等因素——差距的機制尚未定位，且我們自己的 greedy 解碼本身就不確定（±1 pt）。**

**下一步是量上游 vLLM 的 kernel 路線，而不是繼續猜。**
